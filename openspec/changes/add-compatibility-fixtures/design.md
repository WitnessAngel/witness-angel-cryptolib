## Context

See proposal.md for motivation and specs/compatibility-fixtures/spec.md for the requirements. Current state relevant to the approach:

- Legacy reading paths the corpus must pin: `digest_list` RSA-OAEP cipherdicts (`cipher.py`), `payload_signatures` layers (`get_payload_ciphertext_signatures()`, `_validation.py`), `.keystore.json` metadata (`keystore.py`), CANONICAL extjson (`$binary` subtype 04 UUIDs, `$numberInt`), PEMs with legacy PBKDF iteration counts.
- PyPI only has wacryptolib 0.9, 0.10 and 0.11; 0.12 and the 2024 commit before the `payload_signatures` rename (`2328abe`, parent of `b046d02`) exist only in git. Python 3.7–3.14 are installed locally.
- Only symmetric encryption is deterministic. RSA-OAEP, HPKE (ECIES_X25519, ML_KEM_768) and every signature (random or hedged, plus a timestamp) are randomized.
- The existing `tests/fixtures/post_quantum/` fixture is regenerated by `scripts/generate_post_quantum_fixtures.py`, which imports test-module helpers.
- This checkout has `core.autocrlf=true` and the repository has no `.gitattributes`, so text-looking fixtures (PEM, JSON) would be converted to CRLF on Windows checkouts.
- `jsonschema` is already a dependency, and the library already exports cryptoconf and cryptainer JSON-Schemas (`CRYPTOCONF_SCHEMA_JSON`, `CRYPTAINER_SCHEMA_JSON`).

## Goals / Non-Goals

**Goals:**
- A self-describing corpus that a non-Python implementation can consume with a JSON parser plus extjson support for the assets only.
- One generic, data-driven test module: adding a fixture never requires editing test code, as long as its kind already exists.
- Generators that are reproducible enough to *add* generations, but whose outputs are never relied upon to be regenerated identically.

**Non-Goals:**
- JSON-RPC/webserver trustees, revelation requests and other remote-authorization flows.
- Formats older than v0.9 (`.authenticator/`, `.keystore.json`-only authenticators, DES3 PEMs, pre-0.9 signatures). The legacy reading code for them stays, but untested by this corpus.
- Making the MicroPython flightbox consume the corpus. The README makes that possible later.
- Encryption vectors for randomized algorithms (no RNG injection into the library).

## Decisions

### D1. Layout: by fixture kind, then by generation

```
compatibility/
  README.md
  schemas/            _defs.schema.json, plaintext/cipherdict/signature/keystore_pool/
                      cryptoconf/cryptainer .schema.json
  plaintexts/         p00000017.bin (+ .bin.json)
  keystores/          <generation>/ <pool-name>/  (+ <pool-name>.json)
  cipherdicts/        <generation>/<CIPHER_ALGO>/p00000017.cipherdict (+ .json)
  signatures/         <generation>/<SIGNATURE_ALGO>/<name>.signature (+ .json)
  cryptoconfs/        <generation>/<NN_name>.cryptoconf (+ .json); invalid/ subfolder
  cryptainers/        <generation>/<name>.crypt [+ .crypt.payload] (+ .crypt.json)
```

Generation directory names are `<YYYY>_<label>` (e.g. `2022_v0.9_genuine`, `2024_pre_signature_rename`, `2026_relaxed_pq`). They sort chronologically and are self-explanatory without the README. Plaintexts are shared across generations, since they never change. *Alternative*: grouping everything by generation at the top level. Rejected because cross-generation references (an old cryptainer opened with a newer pool) would become awkward, and a kind-first layout lets a consumer that only cares about cipherdicts grab one folder.

Extensions are `.cipherdict`, `.signature`, `.cryptoconf` and `.crypt`, rather than `.json`, so that sidecars (`*.json`) can be told apart from assets by suffix alone, and the `x.json.json` ugliness is avoided.

### D2. Sidecar contents

Every sidecar has a common header, `{"$schema": "../../schemas/<kind>.schema.json", "fixture_kind", "generation", "description", "provenance", "requirements", "asset_sha256"}`, plus kind-specific fields:

- plaintext: `size`, `generator` (`{"algo": "sha256_counter", "seed": "<hex>"}`, i.e. concatenated `SHA256(seed || counter_be32)` blocks truncated to `size`; easy to reproduce in any language)
- cipherdict: `cipher_algo`, `plaintext` (relative path), `direction` (`bidirectional` | `decrypt_only`), and either `symkey` (hex fields, e.g. `{"key", "iv"}`) or `private_key` (`{"keystore_pool", "keystore": "local_keyfactory" | "<authenticator uid>", "keychain_uid", "key_algo", "passphrase"}`)
- signature: `signature_algo`, `message` (path or inline hex), `public_key` (same reference form), `expected_valid`
- keystore_pool: `local_keyfactory` keypairs list, `authenticators: [{keystore_uid, keystore_owner, passphrase, keypairs}]`, `asset_sha256` as a map of relative file path to digest
- cryptoconf: `expected_valid`, `sophistication_level`, `keystore_pool`, `passphrase_mapper`, `min_library_version`
- cryptainer: `plaintext` (path or `plaintext_hex`), `keystore_pool`, `cryptoconf` (optional path), `cryptainer_metadata`, `extjson_flavor` (`canonical` | `relaxed`), `decryption_scenarios: [{name, passphrase_mapper, expected: "success" | "failure", expected_warnings: [error types]}]`

`passphrase_mapper` maps trustee IDs exactly as the library builds them (`authenticator@<uid>`, the `null`-key convention excluded), so the test passes it through unchanged.

`requirements` = `{"algorithms": [...], "pem_protections": [...]}`. The test maps these to backend capabilities (e.g. the fallback backend lacks `ML_KEM_768` and `ML_DSA_65`).

*Alternative*: extjson sidecars. Rejected because sidecars target any consumer, and the assets already carry the extjson burden.

### D3. Schemas: hand-written JSON-Schema 2020-12, with shared `_defs`

`_defs.schema.json` defines `hex`, `uuid`, `relpath`, `sha256`, `provenance`, `requirements`, `passphrase_mapper`, and each kind schema `$ref`s it. Schemas use `additionalProperties: false`, so typos in sidecars fail loudly. The test resolves `$schema` relative to the sidecar through a local `referencing.Registry` (jsonschema 4.18+), with no network access.

The library's own exported cryptoconf/cryptainer schemas are *not* copied into the corpus. They evolve with the library, and asset validity is checked by calling the library itself. *Alternative*: snapshotting them for other implementations. Deferred, since a snapshot would be a second source of truth needing its own drift test.

### D4. Byte-exactness: `.gitattributes` + digests

Add `compatibility/** -text` (binary, no EOL or diff normalization) to a new root `.gitattributes`, so git never converts line endings in the corpus. Each sidecar's `asset_sha256` is checked first by the test, which turns any accidental edit into a precise failure instead of a confusing decryption error.

### D5. Generators: one current-version generator, plus old-release generators

- `scripts/compatibility/generate_current.py <generation_name>` runs in the dev environment with the in-tree library. It produces plaintexts (only missing ones), cipherdicts, signatures, keystore pools, cryptoconfs and cryptainers into a **new** generation directory. It aborts if that directory already exists, writes into a temporary sibling, then renames atomically.
- `scripts/compatibility/generate_legacy_release.py`, run *inside* a throwaway venv (`py -3.9 -m venv`, `pip install wacryptolib==0.9` etc.). It must only use APIs existing in that release (`encrypt_payload_into_cryptainer` / authenticator init / keystore import of the time), writes raw outputs plus a minimal JSON report, and does no corpus formatting. A driver in the dev environment (`scripts/compatibility/build_legacy_generations.py`) creates the venvs, runs it, then wraps the outputs into the corpus layout with sidecars. This keeps sidecar and schema logic in one modern codebase.
- The pre-rename 2024 generation uses `git worktree add <tmp> 2328abe` and the same legacy script, with `PYTHONPATH` pointing at the worktree's `src`.
- Synthesized fallback: if a release does not install (old pinned pycryptodome/bson wheels on a too-recent Python), the driver down-converts current outputs (rename `payload_ciphertext_signatures` → `payload_signatures`, `ciphertext_chunks` → `digest_list`, dump with CANONICAL extjson) and labels provenance `{"method": "synthesized", "legacy_forms": [...]}`. Signatures cover ciphertexts and not field names, so such down-conversions remain verifiable.

Deterministic keys and UIDs: generators use fixed keychain UIDs and keystore UIDs (readable patterns such as `0c0c0c0c-...-0001`) and fixed dummy passphrases (`compat-<owner>-passphrase`), so sidecars are easy to read and diff. Key material itself is random, and is captured once.

*Alternative*: committing the generators' outputs only, with no scripts. Rejected, since future generations need the same tooling.

### D6. Test module: data-driven discovery

`tests/test_compatibility_fixtures.py`:

1. At collection time, glob `compatibility/**/*.json` (excluding `schemas/`), and generate one parametrized test id per sidecar (`kind/generation/name`).
2. Structural tests (not backend-dependent): schema validation, `asset_sha256`, orphan detection, trustee-type check, coverage against `SUPPORTED_CIPHER_ALGOS` / `SUPPORTED_SIGNATURE_ALGOS` / `SUPPORTED_ASYMMETRIC_KEY_ALGOS`.
3. Behavioral tests dispatch on `fixture_kind` to small handler functions (cipherdict, signature, keystore pool, cryptoconf, cryptainer). Keystore pools are `shutil.copytree`-ed into `tmp_path`, which is cached per pool per session to keep runtime low.
4. Backends: the library picks its backend once, at import time, so the module tests the **active** backend only, and maps sidecar `requirements` against that backend's capabilities to decide skips. The fallback leg comes from the existing `py311-fallback` tox env, which uninstalls pycryptodome and runs every test not marked `requires_pycryptodome`. The compatibility module must therefore *not* carry that marker, since its skips are data-driven. *Alternative*: re-running the module in a subprocess with `FORCE_WACRYPTOLIB_FALLBACK_BACKEND=1`, like `test_crypto_backend_parity.py` does. Rejected because it duplicates the tox fallback job and doubles the default test time.
5. A final session-scope check snapshots the corpus file list + mtimes before and after, enforcing "tests leave the corpus untouched".

### D7. Coverage matrix (first population)

| Generation | Provenance | Contents |
|---|---|---|
| `2022_v0.9_genuine` (+ `v0.10`, `v0.11`) | genuine release | RSA-only pool (local keyfactory + 2–3 authenticators, RSA_OAEP/RSA_PSS/ECC_DSS/DSA_DSS), cryptainers: simple AES, multi-layer, Shamir 2-of-3 over authenticators, signed, offloaded; CANONICAL extjson, `payload_signatures` |
| `2024_pre_signature_rename` | genuine worktree (or synthesized) | same pool reused, cryptainers with `payload_signatures` + `payload_plaintext_signatures` absent |
| `2026_current` | current | all cipherdicts × plaintext sizes (+ legacy `digest_list` vector, synthesized), all signatures, cryptoconf levels 01–07 + invalid set, RELAXED cryptainers incl. `payload_plaintext_signatures`, `cryptainer_metadata`, recursive symmetric key layers |
| `2026_post_quantum` | migrated + current | migrated `pq_hybrid_cryptainer.crypt` and its pool, plus a pool with ECIES_X25519/ML_KEM_768/ML_DSA_65 authenticators and hybrid cryptainers |

Plaintext sizes: per the spec. The 1 MiB plaintext only gets symmetric cipherdicts (3 algos) and 2–3 cryptainers, which keeps the corpus around 10–15 MB.

### D8. Migration of `tests/fixtures/post_quantum/`

Use `git mv` into `compatibility/cryptainers/2026_post_quantum/pq_hybrid_cryptainer.crypt` and `compatibility/keystores/2026_post_quantum/pq_hybrid_pool/`, and add sidecars. `test_pq_hybrid_fixture_cryptainer_decryption` becomes redundant with the generic test and is removed. `PQ_FIXTURES_DIR` and `_build_pq_hybrid_cryptainer` stay for the two in-memory PQ tests, which do not use files. Then delete `scripts/generate_post_quantum_fixtures.py`.

## Risks / Trade-offs

- [Old releases fail to install on available Pythons (native wheels for old pycryptodome/pymongo)] → Try Python 3.9, then 3.8/3.7. Otherwise fall back to synthesized fixtures, recorded in provenance (accepted by the user).
- [Old release APIs differ (argument names, trustee conf keys)] → The legacy script is small and version-switched. It is time-boxed per release, with synthesized fallback.
- [Repo size grows by ~10–30 MB permanently, since fixtures are append-only] → Restrict 1 MiB vectors to symmetric algos and a few cryptainers, do not duplicate plaintexts across generations, and reuse keystore pools across generations.
- [Fallback-backend run is slow on large RSA/DSA decryptions and 1 MiB symmetric data in pure Python] → Mark the 1 MiB cases `slow` for the fallback backend, and keep asymmetric vectors at ≤ 4 KiB.
- [A future intentional format break would fail the suite] → Intended. The fix is to keep a reading path, or to mark the fixture `expected: "failure"` in a *new* superseding sidecar policy decided then, never by editing old fixtures.
- [Committed private keys and passphrases could be mistaken for real secrets by scanners] → All of them are dummy, documented in the README, and owner names are prefixed `compat-`.
- [Sidecar schema evolution: adding a field to a kind invalidates nothing, but making one required would invalidate old sidecars] → New required fields are only allowed with a new schema version (`cryptainer.v2.schema.json`); old sidecars keep pointing at their own `$schema`.

## Migration Plan

Additive only. Land `.gitattributes` before the first fixture commit. Migrate the PQ fixture in the same change. Rollback is a revert, since no library code changes.
