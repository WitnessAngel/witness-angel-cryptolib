## Purpose

Defines when cryptoconfs and cryptainers are validated, so that each structure is validated once at its point of entry in a process, and the knowledge is remembered afterwards instead of being re-derived by every layer.

## ADDED Requirements

### Requirement: Validate once at ingress, remember in-process
The system SHALL validate a cryptoconf or cryptainer when it enters a public operation as an untagged dict, and SHALL remember that validation by tagging a snapshot of it as a validated structure. A structure already tagged as validated SHALL NOT be validated again by any later step of the same process. The tag SHALL be an internal detail: public functions SHALL keep accepting plain dicts.

#### Scenario: Raw cryptoconf is validated exactly once per encryption
- **WHEN** a plain cryptoconf is passed to an encryption entry point, for example through the CLI or `encrypt_payload_into_cryptainer`
- **THEN** it is validated one time in total, regardless of how many internal layers it traverses

#### Scenario: Default cryptoconf of a storage is validated once
- **WHEN** a `CryptainerStorage` is created with a `default_cryptoconf` and many files are then enqueued without their own cryptoconf
- **THEN** the default cryptoconf is validated once, at construction, and not again for any enqueued file

#### Scenario: Invalid input is still refused at the entry point
- **WHEN** an invalid cryptoconf or cryptainer is passed as a plain dict
- **THEN** a `SchemaValidationError` is raised before any key generation, network access or payload processing

### Requirement: Tags do not survive copying or serialization
The system SHALL NOT propagate a validation tag to derived or reloaded data. Deep-copying a tagged structure SHALL yield a plain dict, and data loaded from JSON or from the filesystem SHALL be untagged and therefore validated at ingress.

#### Scenario: Cryptainer derived from a cryptoconf is not a validated cryptoconf
- **WHEN** the flightbox deep-copies a validated cryptoconf to build a cryptainer base
- **THEN** the copy is a plain dict, and carries neither the cryptoconf nor the cryptainer tag

#### Scenario: Loaded cryptainer is validated
- **WHEN** a cryptainer is dumped to JSON or to the filesystem and loaded back
- **THEN** the loaded object is untagged, and is validated when it enters decryption or analysis

### Requirement: Trust of tags inside a process
The system SHALL trust a validation tag without re-validating the structure, since protection against in-process tampering is out of scope. A cryptainer generated by the encryptor from a validated cryptoconf SHALL be tagged as validated without being validated again.

#### Scenario: Encrypt then decrypt in the same process
- **WHEN** a cryptainer returned by an encryption function is passed directly to a decryption function
- **THEN** it is not validated again

### Requirement: Strictness is part of the cryptainer tag
A validated cryptainer SHALL record whether its payload ciphertext was required to be inline. A strictly validated cryptainer SHALL satisfy a lenient requirement, but a leniently validated cryptainer SHALL NOT satisfy a strict one, and SHALL be re-validated strictly when a strict check is requested.

#### Scenario: Lenient token used for decryption
- **WHEN** a cryptainer validated leniently (payload absent or offloaded, as for `gather_decryptable_symkeys`) is passed to payload decryption
- **THEN** it is validated strictly before use, and refused if its payload ciphertext is not inline bytes

#### Scenario: Strict token used for analysis
- **WHEN** a strictly validated cryptainer is passed to `gather_decryptable_symkeys`
- **THEN** it is accepted without any further validation
